# Inter-Casino: парные записи с правильными знаками

## Что не так сейчас
Страница Inter-Casino пишет одну строку в журнал кошельков с `kind = 'inter_casino'`. В базе разрешены только виды `income / expense / change_in / change_out / transfer_in / transfer_out / reversal / adjustment`, поэтому такая запись **вообще не сохраняется** (ошибка проверки) — записей этого вида в базе 0. Второй стороны перевода тоже нет: получающее казино ничего не видит.

## Как будет
Перевод становится двусторонним:

1. **Отправитель** создаёт перевод: выбирает свой кошелёк, казино-получателя, сумму, дату, комментарий.
   Сразу пишется одна запись `transfer_out` с **отрицательной** суммой — деньги ушли, баланс кошелька уменьшается немедленно.
2. **Получатель** (в своём казино, на этой же странице, вкладка «Incoming») видит ожидающий перевод, выбирает кошелёк зачисления и подтверждает.
   Пишется парная запись `transfer_in` с **положительной** суммой на выбранный кошелёк.
3. До подтверждения перевод виден как «Pending» с обеих сторон и не влияет на баланс получателя.
4. Отправитель может отменить неподтверждённый перевод, получатель — отклонить: тогда исходная `transfer_out` сторнируется обратной записью (без удаления, аудит сохраняется).

**Валюта:** зачисление возможно только на кошелёк той же валюты, что и у отправляющего (список кошельков получателя фильтруется). Разные валюты не смешиваем, курс не выдумываем.

**Балансы:** знак несёт сама сумма (`transfer_out` — минус, `transfer_in` — плюс), как уже принято для существующих переводов. Расчёт балансов кошельков и отчёты подхватывают это без дополнительных правок.

## Технические детали
- Новая таблица `fin_inter_casino_transfers` (шапка перевода): `id`, `from_casino_id`, `from_wallet_id`, `to_casino_id`, `to_wallet_id (null до подтверждения)`, `amount`, `currency`, `business_date`, `note`, `status ('pending' | 'accepted' | 'rejected' | 'cancelled')`, `out_tx_id`, `in_tx_id`, `created_by`, `accepted_by`, `accepted_at`, `created_at`. GRANT для `authenticated`/`service_role`, RLS: видит и создаёт тот, у кого есть доступ к казино-отправителю или казино-получателю (через существующую проверку доступа к казино); изменение статуса — только сторона получателя (accept/reject) и отправитель (cancel).
- Две SECURITY DEFINER RPC (`search_path = public`), чтобы обе стороны писались атомарно и в чужое казино:
  - `fin_inter_casino_send(...)` — создаёт шапку + `fin_wallet_tx` `transfer_out` (amount = −сумма, `amount_tzs` по `fx_rate` кошелька, `ref_table='fin_inter_casino_transfers'`, `ref_id`).
  - `fin_inter_casino_accept(transfer_id, to_wallet_id)` — проверяет совпадение валюты, пишет `transfer_in` (+сумма) в кошелёк получателя, ставит `status='accepted'`.
  - `fin_inter_casino_reject(transfer_id, reason)` / `fin_inter_casino_cancel(...)` — сторнирующая запись на кошелёк отправителя (`kind='reversal'`, `reversal_of = out_tx_id`), статус меняется.
- `src/pages/finances/FinancesInterCasinoPage.tsx`: переписан на две вкладки — «Transfers» (журнал: дата, из казино/кошелька, в казино/кошелёк, сумма со знаком и цветом, статус) и «Incoming» (ожидают подтверждения для активного казино, кнопка Accept с выбором кошелька, Reject). Форма создания получает поля «Казино-получатель» и убирает ручной выбор IN/OUT.
- Новый хук `src/hooks/use-inter-casino.ts` (список, send, accept, reject, cancel) с `invalidateFinance` после мутаций.
- Старый вид `kind='inter_casino'` больше не используется (записей с ним в базе нет, миграция данных не нужна).
- Проверка: типизация + пробный перевод между двумя казино с контролем балансов кошельков до/после.
