# Аудит доступа между казино (Expenses, результаты, слоты)

## Что подтверждено проверкой БД

Почти все правила доступа привязаны к **основному казино из профиля** (`get_user_casino_id`), а не к реальному списку доступных казино:

- `expenses`: чтение для super_admin есть, но **изменение/удаление/подтверждение** — только для основного казино (`casino_id = get_user_casino_id(...)`). Отсюда «кнопка Expenses работает криво».
- `transactions`, `shifts`, `cash_counts`, `table_daily_results` — читаются только по основному казино (кроме отдельных исключений для super_admin / surveillance / boss). У **general_manager** сквозного правила нет вообще → пустые цифры.
- Все таблицы слотов `cage_slots_*` (`cage_slots_shifts`, `cash_counts`, `cash_inventory`, `cards`, `tips_cd`, `settings`, `exchange_rates`, `comments`) идут через `cs_can_view`, где жёстко зашито основное казино. GM и менеджер с доступом к другому казино не видят результат слотов.
- Ещё в списке «только основное казино»: `casino_visits`, `players` (update), `player_daily_zones`, `player_day_drop_cache`, `casino_settings`, `casino_license`, `pit_book_reads`, `pos_purchases`, `table_day_drop_cache`.
- Функция `user_has_casino_access` знает только про super_admin и finance_manager — **boss и general_manager в неё не попадают**.
- В интерфейсе `hasGlobalAccess` (`src/lib/casino-context.tsx`) перечисляет super_admin / finance_manager / surveillance / boss — **general_manager отсутствует**, поэтому список казино у GM строится только из выданных строк доступа.

Поэтому в Arusha (основное казино этих пользователей) всё работает, а в Mwanza / Dodoma / Mbeya часть данных пустая: то, что читается по «глобальным» правилам (drop-кэш открыт всем), приходит, а результаты и расходы — нет.

## Что делаю

### 1. Единая функция доступа (БД)
Ввожу `public.has_casino_scope(_uid, _casino_id)`: доступ есть, если
- казино совпадает с основным в профиле, **или**
- есть строка в `user_casino_access`, **или**
- у роли есть возможность «видеть все казино» (super_admin, general_manager, finance_manager, boss).

Обновляю `user_has_casino_access`, чтобы она опиралась на ту же логику (boss и general_manager перестают выпадать).

### 2. Переписываю политики доступа
Для всех таблиц, где сейчас стоит «только основное казино», меняю условие на `has_casino_scope(...)`, сохраняя ролевые ограничения (кто именно может писать):
- Расходы: чтение, подтверждение, редактирование и удаление — по доступному казино, а не по основному.
- Смены, транзакции, пересчёты кассы, результаты столов, визиты, зоны игроков, настройки казино.
- Слоты: `cs_can_view` / `cs_can_write` / `cs_can_approve` переводятся на ту же проверку доступа.

Права на запись при этом не расширяю за пределы существующих ролей — меняется только «какое казино», а не «кто».

### 3. Правки интерфейса
- В `src/lib/casino-context.tsx` добавляю `general_manager` в глобальный доступ, чтобы у GM в переключателе были все казино.
- Проверяю, что страницы Expenses и результаты используют активное казино из контекста (переключение подкачивает данные без перезагрузки).

### 4. Проверка
- Прогон SQL-проверки: для тестовых пользователей (super_admin, GM, менеджер с доступом) сравниваю количество видимых расходов/смен/результатов по каждому казино.
- Запуск security-линтера после миграции.
- Живая проверка страницы Expenses и результатов слотов на Mbeya.

## Технические детали
- Одна миграция: новая функция + пересоздание политик (DROP/CREATE) на перечисленных таблицах.
- `has_casino_scope` — `STABLE SECURITY DEFINER`, `search_path = public`, чтобы не ломать RLS-рекурсию.
- Публичные гранты не трогаю: таблицы уже доступны через Data API.
