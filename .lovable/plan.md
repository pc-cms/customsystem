# Аудит сетевых учёток: что осталось после перевода правил доступа

## Что уже в порядке (проверено в базе)

- Ни одно правило доступа (RLS) больше не сравнивает казино с «домашним»: 0 политик с `get_user_casino_id`, все переведены на `has_casino_scope`.
- `has_casino_scope` даёт доступ сетевым ролям (super_admin, general_manager, finance_manager, boss, surveillance), плюс по списку доступа и по домашнему казино.
- Сетевые учётки имеют явный доступ ко всем 4 казино: Super Admin, GM, Igor, Michael, Finance, Vladimir/Alex/Andrew/CCTV, Account Manager.
- Локальные учётки (Daniyar — Mbeya, Michael Mwanza — Mwanza+Mbeya, Pasha — Mbeya, кассиры/питы/ресепшн) не расширены.

## Что упущено — действия, а не чтение

Правила чтения починили, но **действия** идут через служебные функции, где всё ещё зашито домашнее казино. Отсюда «кнопка есть, а действие ругается».

1. **Слоты: запись и подтверждение.** `cs_can_write` и `cs_can_approve` разрешают работу только в домашнем казино (исключение только для Super Admin). GM, Igor, Michael, Finance видят смену слотов на чужом казино, но не могут ни сохранить, ни подтвердить.
2. **Подтверждение расхода.** `approve_expense_as_manager` жёстко бросает «Casino mismatch», если расход не из домашнего казино — даже для Super Admin. Это и есть кривая кнопка Expenses на Mwanza/Mbeya/Dodoma.
3. **Перевод фишек между игроками.** `create_chip_transfer_pair` не принимает казино, а подставляет домашнее из профиля. Менеджер сети, работая на Mbeya, запишет перевод фишек в Arusha — это уже порча данных, а не только отказ доступа.
4. **Правка снимка закрытия дня.** `edit_business_day_snapshot` пускает только домашнее казино (кроме Super Admin) — GM и Finance не смогут править чужой день.
5. **Удаление сотрудника.** `hr_delete_employee` — то же: только домашнее казино, кроме Super Admin.
6. **Создание расчётного периода зарплат.** `payroll_create_period` — HR не может создать период вне домашнего казино (для Finance/Super Admin проходит).
7. **Закупки бара.** `pos_create_purchase` бросает «Casino mismatch» на чужом казино.
8. **Лишний аудит.** Триггер `log_cross_casino_player_edit` считает любую правку сетевой учёткой «межказинной» и засоряет журнал; GM, boss, finance не исключены.
9. **Дубли профилей.** У «Account Manager» и «Pasha» по две строки в профилях. `get_user_casino_id` берёт `LIMIT 1` без сортировки, поэтому домашнее казино может «плавать» между запросами.

## Что делаю

### 1. Единое правило для действий
Перевожу все перечисленные функции на ту же проверку `has_casino_scope(auth.uid(), <казино строки>)`, сохраняя ролевую часть без изменений:
- `cs_can_write`, `cs_can_approve` — доступ по scope + прежний набор ролей.
- `approve_expense_as_manager`, `edit_business_day_snapshot`, `hr_delete_employee`, `payroll_create_period`, `pos_create_purchase` — вместо сравнения с домашним казино проверка scope по казино самой записи.
- `create_chip_transfer_pair` — добавляю необязательный параметр казино: берётся казино стола/игрока, при его отсутствии — домашнее; и проверяется через scope. Вызов на фронте передаёт активное казино.
- `log_cross_casino_player_edit` — не пишет запись, если у редактора сетевой доступ.

### 2. Чистка дублей профилей
Убираю дублирующие строки профилей (оставляю актуальную) и добавляю уникальность по пользователю, чтобы домашнее казино было однозначным.

### 3. Проверка остальных служебных функций
Отдельно прохожу функции, которые берут казино напрямую из профиля (не через `get_user_casino_id`), и вставки, где казино подставляется по профилю вместо активного — по тому же принципу.

## Технические детали
- Одна миграция: `CREATE OR REPLACE FUNCTION` для 8 функций (все `SECURITY DEFINER`, `search_path = public`), плюс дедупликация `profiles` и уникальный индекс по `user_id`.
- Сигнатура `create_chip_transfer_pair` расширяется параметром с значением по умолчанию — существующие вызовы не ломаются; фронт (`src/components/...` вызов перевода фишек) обновляется на передачу активного казино.
- RLS-политики и гранты не трогаются.
