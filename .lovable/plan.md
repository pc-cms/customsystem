# Глубокий аудит «тихих обрезаний» данных — работы завтра в 10:00 EAT

Работы выполняем **завтра в 10:00 EAT, после закрытия финансовых дней**. Изменения только на стороне чтения данных — записи, миграций и правок в базе не будет, поэтому окно безопасное.

## 1. Как это работает сейчас (главное, что нужно понять)

Никакого «второго запроса» и «комбайна» нет. Логика такая:

1. Экран отправляет **один** запрос в API.
2. Сервер (PostgREST) физически не отдаёт больше **1000 строк** за ответ. Если подходящих строк 5 000 — придёт 1000, тихо.
3. **Ошибки не будет**, HTTP 200, массив просто короче. Ни экран, ни код не узнают, что данные обрезаны.
4. Дальше браузер считает суммы/итоги **по тому, что пришло**. То есть цифра не «не считается» — она считается, но по неполному набору строк. Это самое опасное: отчёт выглядит нормальным, а сумма занижена.
5. Дозагрузки страниц нет нигде, кроме двух мест, где она написана вручную: `src/lib/fetch-paged.ts` (цикл `.range()` по 1000) и `src/lib/chip-snapshots.ts` (`fetchChipSnapshots`). Всё остальное — один запрос.

Дополнительно: `.limit(2000)`, `.limit(5000)`, `.limit(10000)` в коде — **фикция**. Сервер всё равно вернёт 1000. То есть места, где кто-то «на всякий случай поставил большой лимит», на деле уже обрезаны.

Про списки и открытие карточки: списки страдают, карточка — нет. Открытие конкретной записи (игрок, смена, снапшот) грузится отдельным запросом по id и всегда полное. Проблема именно в списках и в итогах, которые считаются по спискам.

## 2. Что реально сломано сейчас (проверено запросами к базе)

### A. Фишки в отчёте по смене — обрезаны гарантированно
`chip_snapshots` за один бизнес-день по одному казино: **до 10 857 строк** (Arusha 20.05), типично 3 000–5 900.

- **Shift Closing Report**: запрос без сортировки и без пагинации → придут случайные 1000 из ~5 000. Логика берёт «последний снапшот по столу/номиналу» — а последнего в этой тысяче может не быть.
- **Edit / Reprint Shift**: то же самое, но с сортировкой **по возрастанию** времени → приходит самая **старая** тысяча, то есть свежие подсчёты фишек не попадают в отчёт почти наверняка.
- Итог: результат по фишкам за смену считается по неполным данным. Это прямое влияние на цифры смены.
- Рядом уже есть правильный хелпер `fetchChipSnapshots` (постранично) — просто эти два места его не используют.

### B. Балансы кошельков в режиме «All casinos» — обрезаны
`fin_wallet_tx`: всего **1 285** проведённых движений, по одному казино максимум 580.

- По конкретному казино сумма сейчас считается **правильно** (580 < 1000).
- В сводном режиме (все казино) запрос идёт без фильтра → приходит 1000 из 1285, и **285 движений просто не участвуют в сумме**. Office Safe и Finance Dashboard в сводном режиме показывают заниженные остатки.
- Важно: страница Balance (Expected/Actual) считает через серверный RPC `fin_balance_snapshot` и **не затронута** — там всё считает база.

### C. Игроки — обрезаны
Игроков в Arusha **1 166**. Все места, где грузится «весь список игроков по казино» одним запросом (префетч, справочник имён в Logs, поиск дублей, объединение двойников), видят только 1000. Отсюда: игрок «не находится», дубли не показываются, имя в логе пустое.

### D. Фиктивные лимиты > 1000 — уже режут отчёты
Заявлено 2000/3000/5000/10000, приходит 1000: Monthly Report, Category MTD, Daily Expenses, Expenses, Incidents, Blacklist, Promo Codes / Issuance / Redemptions / Expiry, Lottery Sales, Cashback, AM Budget, Finances Wallets. Пока не все из них перевалили за 1000 строк, но лимит уже не работает как задумано.

### E. Лимиты, которые малы сами по себе (не 1000, а руками поставленные)
- **Cage · Transactions**: `limit(200)` на бизнес-день, а в пике уже **163 транзакции за день** по Arusha. То есть до обрезания буквально пара дней роста.
- **Cashless** без даты: `limit(200)`, всего по казино 1 272.
- **Logs**: 500 последних из 80 422 по казино — как «лента» нормально, но поиск по логам ищет только внутри этих 500.
- **Finances · Expenses / Wallet TX**: `limit(500)`, при годовом диапазоне по Arusha уже **755 расходов за 2026** → Budget vs Actual и Budget Difference считают по неполному году.

### F. Проверено и НЕ является проблемой (чтобы не тратить время)
- Break List: максимум **524** строки на казино/день (94 тыс. — это за всю историю, грузится всегда один день).
- Rota / Attendance за месяц: 550–810 строк — пока проходят, но берём в работу как профилактику.
- Table Tracker (317/день), Casino Visits (127/день), Client Sessions (единицы/день), Table Daily Results — в порядке.
- `usePlayers` (общий список игроков) уже постраничный — работает верно.
- `maxLength` в полях ввода и `slice(0, N)` в списках — косметика, логику не ломают.

## 3. План работ (в порядке выполнения)

**Шаг 1 — цифры смены (критично)**
Перевести `ShiftClosingReport` и `EditReprintShiftPage` на существующий `fetchChipSnapshots` (постранично). Сверить итог по фишкам одной закрытой смены до и после — цифра должна измениться в сторону правильной.

**Шаг 2 — деньги**
- `useFinWalletBalances`: считать сумму на сервере (агрегат в базе) вместо выкачивания строк. Заодно быстрее.
- `useFinExpenses` / `useFinWalletTx`: `limit(500)` → постраничная загрузка по выбранному периоду.

**Шаг 3 — игроки**
Префетч игроков, справочник в Logs, поиск дублей и объединение — на `fetchPaged`.

**Шаг 4 — отчёты**
Убрать все `limit > 1000`; где нужен только итог — считать на сервере, а не тянуть строки в браузер.

**Шаг 5 — мелкие лимиты**
Cage Transactions 200 → полный бизнес-день постранично. Cashless без даты → период вместо «последних 200». В Logs добавить серверный поиск, чтобы не искать внутри 500 строк.

**Шаг 6 — защита от повторения**
Автотест, который валит сборку при появлении `.limit(N > 1000)` или запроса без пагинации к крупным таблицам (chip_snapshots, transactions, players, activity_logs, expenses, fin_wallet_tx, cashless_transactions, casino_visits, breaklist, table_tracker). Плюс убрать дубль `fetchPaged` внутри `use-players.ts`.

## 4. Технические детали

- Потолок задаётся PostgREST (`db-max-rows = 1000`), поменять его со стороны приложения нельзя и не нужно — правильное решение это пагинация и серверные агрегаты.
- Паттерн: `.range(from, to)` в цикле через `src/lib/fetch-paged.ts`, либо RPC/представление с `sum()`.
- Для страниц-лент (Logs, Cage Transactions) пагинация должна быть «по требованию» (кнопка/скролл), а не выкачивание всего — иначе просадим скорость.
- Версия приложения будет повышена, изменения только фронтенд + при необходимости пара read-only агрегатов в базе.
