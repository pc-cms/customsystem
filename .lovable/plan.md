# Зафиксировать неизменное правило Expected — только Arusha

## Цель

Ничего не менять в данных и коде, пока не утверждена одна каноническая формула. Проверка и последующий разбор относятся **только к Arusha за август 2026**. Другие филиалы не трогаем.

## Текущая формула в системе

```text
Expected =
  Opening Float
+ Table Result закрытых бизнес-дней
+ Slots CashDesk Win закрытых бизнес-дней
+ Office Commissions
+ Tips & Bonuses (signed)
+ Office movements (investment / owner_topup / office)
+ Add Float
+ JP (signed)
+ Chip Miss
+ Card Miss
− Approved Expenses
− Collections
− Accepted inter-casino transfers / money change
```

`Card Balance` и `Slots System / Net Win` в Expected не входят.

`Actual = сумма последних физических пересчётов кошельков`.

`Variance = Actual − Expected`.

## Предлагаемое железное правило

```text
Expected = Opening Float
         + реальные ПРИХОДЫ
         − реальные РАСХОДЫ
```

### Входит в Expected

- Закрытые игровые результаты: Table Result и Slots CashDesk Win.
- Реальные доходы/приходы Office: Commissions, Tips & Bonuses IN, JP IN и другие утверждённые категории дохода.
- Реальные расходы Office: approved Expenses, Tips & Bonuses OUT, JP OUT и другие утверждённые категории расхода.
- Collection — signed приход/расход по своему бизнес-смыслу.
- Add Float — только если это реальные новые деньги, добавленные в филиал, а не перенос между его кошельками.
- Межфилиальный перевод — только потому, что деньги реально пришли в филиал или ушли из него.

### Никогда не входит в Expected

- `adjustment` / ADJ — меняет только Actual.
- Любое перемещение денег между кошельками одного филиала: Cash → Bank, Bank → Cash, Wallet → Wallet.
- Физический пересчёт.
- Card Balance.
- Slots System / Net Win.
- Открытая кассовая смена и её расходы/доходы до закрытия бизнес-дня.

Ключевой принцип: **движение внутри Arusha не создаёт ни приход, ни расход Arusha и поэтому не меняет общий Expected.** Оно может менять распределение Expected по кошелькам, но сумма Expected филиала остаётся неизменной.

## Следующий этап после утверждения правила

1. Вывести все транзакции Arusha за август по группам: реальные приходы, реальные расходы, внутренние движения, ADJ.
2. Для каждой спорной записи показать текущий источник и текущее влияние на общий Expected.
3. Согласовать классификацию построчно.
4. Только после отдельного подтверждения подготовить минимальное исправление данных/формулы только для Arusha.

## Ограничения

- Сейчас никаких изменений данных, функций или интерфейса.
- Никаких изменений в Dodoma, Mwanza и Mbeya.
- Не переклассифицировать автоматически исторические IN/OUT в ADJ.
- Не считать внутреннее движение доходом или расходом филиала.
