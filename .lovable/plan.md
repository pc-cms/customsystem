# Аудит «скрытых ограничений» в запросах

Проверил весь проект. Проблема из Blacklist — не единичная: API отдаёт максимум **1000 строк за один ответ**, и в коде есть 282 запроса без пагинации плюс 15+ запросов с «фиктивными» лимитами (`limit(2000)`, `limit(5000)`, `limit(10000)`), которые на самом деле молча обрезаются до 1000.

## Что подтверждено данными (не догадки)

Реальные объёмы в базе на сегодня:

| Данные | Объём | Где обрезается |
|---|---|---|
| Chip snapshots за день | 2 300–5 900 строк | Shift Closing Report, Edit/Reprint Shift |
| Break List за день | 1 226–1 273 строки | префетч Break List |
| Игроки Arusha | 1 166 | префетч игроков, поиск дублей, объединение, справочник в Logs |
| Транзакции за месяц | 3 500–4 000 | Tips, отчёты по транзакциям |
| Fin wallet tx (всего) | 1 285 | расчёт балансов кошельков |
| Rota / Attendance за месяц | 550–810 | пока проходит, но близко к потолку |

Отдельно: любой `.limit(N)` с N > 1000 обрезается сервером до 1000 — то есть 5 отчётов (Promo, Lottery, Cashback, AM Budget, Monthly Report) уже сейчас могут показывать неполные цифры без каких-либо ошибок на экране.

## Что делаю

### 1. Критично — цифры считаются неверно
- **Chip snapshots** (Shift Closing Report, Edit/Reprint Shift): перевести на постраничную выборку. Сейчас отчёт по фишкам за смену физически не может получить все строки.
- **Fin wallet tx**: сумма по кошелькам считается на клиенте по обрезанному списку — перенести агрегат на сервер (SUM в БД), а не тянуть строки.
- **Транзакции за период** (Tips, месячные отчёты): постраничная выборка вместо `limit(2000)`.
- **Break List / префетч игроков**: постраничная выборка.

### 2. Убрать все «врущие» лимиты
Заменить `limit(2000/3000/5000/10000)` на постраничную загрузку или серверный агрегат в: Monthly Report, Category MTD, Daily Expenses, Expenses, Incidents, Blacklist, Promo Codes/Issuance/Redemptions/Expiry, Lottery Sales, Cashback, AM Budget, Finances Wallets, Bank Checks, Reports.

### 3. Отчёты — считать на сервере, а не в браузере
Там, где нужен только итог (суммы, средние, количества), вместо выкачивания тысяч строк использовать серверный подсчёт. Это заодно ускорит страницы, которые сейчас грузятся секундами.

### 4. Защита от повторения
- Добавить автотест, который падает при появлении в коде `.limit(N > 1000)` или запроса без пагинации к «крупным» таблицам (transactions, players, chip_snapshots, breaklist, activity_logs, casino_visits, table_tracker, expenses и др.).
- Единый хелпер `fetchPaged` — обязателен для любых выборок «все строки за период».

### 5. Наблюдение (без изменений сейчас)
Rota, Attendance, Table Tracker, Casino Visits ещё не превысили 1000, но растут — их переведём на пагинацию в этом же проходе, чтобы не ловить ту же ошибку через месяц.

## Технические детали

- Потолок 1000 строк задаётся PostgREST (`db-max-rows`); `.limit()` больше него не помогает — ответ приходит без ошибки, просто короче.
- Паттерн исправления: `.range(from, to)` в цикле через `src/lib/fetch-paged.ts` (page size 1000), либо RPC с агрегатом.
- В `src/hooks/use-players.ts` есть локальная копия `fetchPaged` — убрать дубль, использовать общий хелпер.
- Ограничения интерфейса (`maxLength`, `slice(0, N)` в списках) проверил — они косметические и логику не ломают, кроме `FloorTipsReport` (`slice(0,100)`) и `PosManagerRecipes` (`slice(0,50)`), где список визуально обрезан без подсказки; добавлю счётчик «показано X из Y».
- Версия приложения будет повышена.

## Порядок работ

1. Блок «критично» (фишки, кошельки, транзакции, Break List, игроки).
2. Замена всех лимитов > 1000.
3. Серверные агрегаты для тяжёлых отчётов.
4. Автотест-страж + чистка дублей.
