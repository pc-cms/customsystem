# Единая модель доступа: сетевые учётки vs учётка одного казино

## Новая логика (простая)

Убираем понятие «домашнее казино» как основу доступа. Остаётся два типа учёток:

1. **Сетевая** — работает на любом поддомене одинаково, данные всегда берутся из того казино, на чьём поддомене человек находится.
2. **Локальная (одно или несколько конкретных казино)** — вход разрешён только на своих поддоменах. На чужом поддомене вход отклоняется с сообщением о недоступности, а не пускает внутрь с пустыми экранами.

Поле «домашнее казино» в профиле остаётся только как значение по умолчанию (куда бросить при заходе с общего адреса), но **правами больше не управляет**.

## Что показала проверка

- Правила доступа в базе почти везде сравнивают казино с «домашним» из профиля (`get_user_casino_id`), поэтому GM/Super Admin на Mwanza, Dodoma, Mbeya видят пустые расходы и результаты, а на Arusha (их домашнее) всё работает.
- Расходы: чтение суперадмину открыто, но подтверждение/правка/удаление — только по домашнему казино. Отсюда «кнопка Expenses работает криво».
- Все таблицы слотов (`cage_slots_*`) идут через проверку, где домашнее казино зашито жёстко — результат слотов у GM на других казино не грузится.
- Функция проверки доступа знает только super_admin и finance_manager; boss и general_manager в неё не попадают.
- В интерфейсе список «глобальных» ролей не содержит general_manager.

## Сетевые учётки (по текущей базе)

Полный доступ ко всем казино: **admin (Super Admin), gm (General Manager), igor (Boss), michael (Manager + Finance)**.

Сейчас строки доступа на все казино есть также у: surveillance (alex, andrew, cctv, vladimir), account manager (amanager). Оставляю их сетевыми — они и раньше работали по всей сети. `michaelm` остаётся с доступом к Mwanza + Mbeya (локальная на два казино), все остальные — только своё казино.

## Что делаю

### 1. База: одна функция доступа
Ввожу `public.has_casino_scope(_uid, _casino_id)` — доступ есть, если казино есть в списке доступа пользователя (`user_casino_access`), либо это его казино из профиля, либо у роли есть право «вся сеть» (super_admin, general_manager, finance_manager, boss, surveillance).

Дополнительно заполняю `user_casino_access` для сетевых учёток по всем казино, чтобы список был явным, а не выводился из роли.

### 2. База: переписываю правила доступа
Везде, где стоит сравнение с домашним казино, ставлю проверку доступа: расходы (чтение, подтверждение, правка, удаление), смены, транзакции, пересчёты кассы, результаты столов, визиты, зоны игроков, настройки казино, кэш дропа, а также весь блок слотов (`cs_can_view` / `cs_can_write` / `cs_can_approve`). Ролевые ограничения «кто может писать» не расширяю — меняется только «в каком казино».

### 3. Интерфейс: жёсткая привязка к поддомену
- В `src/lib/casino-context.tsx` активное казино = казино поддомена, всегда; general_manager добавляется в сетевые роли.
- Если у пользователя нет доступа к казино этого поддомена — показываем экран «This account has no access to <Casino>» с кнопкой выхода, вместо пустого интерфейса. Логика применяется сразу после входа.
- Переключатель казино показывается только сетевым учёткам и учёткам с несколькими казино.

### 4. Проверка
- SQL-сверка: для admin, gm, igor, michael считаю количество видимых расходов/смен/результатов/смен слотов по каждому казино — должно совпадать с фактическим количеством строк.
- Для локальной учётки (например, `livemb`) проверяю, что на чужом поддомене доступ закрыт.
- Запуск security-линтера и живая проверка Expenses и результатов слотов на Mbeya.

## Технические детали
- Одна миграция: функция + пересоздание политик (DROP/CREATE) на перечисленных таблицах + заполнение `user_casino_access` для сетевых учёток.
- `has_casino_scope` — `STABLE SECURITY DEFINER`, `search_path = public`.
- Гранты Data API не трогаю.
