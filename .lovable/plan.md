# Super Admin: видимость и удаление кассовых расходов

## Подтверждённое состояние

- Проблема воспроизводится для пользователя, вошедшего с ролью **Super Admin**, на экранах `/expenses` и `/expenses/approvals` конкретного филиала.
- В базе расходы есть: за 28/08–02/09 имеются строки Arusha, Mwanza, Dodoma и Mbeya.
- Backend-доступ настроен: Super Admin имеет глобальный SELECT по `expenses`; отдельная политика разрешает Super Admin hard delete. Права модулей `expenses` и `expenses_approvals` также включены.
- Запросы обоих экранов дополнительно фильтруются по активному `casino_id`; `/expenses` также фильтруется по сохранённым датам, source и status, а `/expenses/approvals` показывает только `approved = false`.
- Найден отдельный UI-дефект: `isManager` не включает Super Admin, поэтому на `/expenses` у него скрыты управленческие колонки и действия. Это не объясняет пустой ответ базы, но обязательно должно быть исправлено.

Точная причина пустого списка ещё не доказана без запуска экрана под реальной сессией Super Admin. Возможны две проверяемые ветки: неверный активный филиал при первом рендере либо сохранённые фильтры `/expenses`; на Approvals пустой список может быть корректным, если в филиале нет pending-строк.

## План действий

1. **Воспроизвести под Super Admin на домене филиала**
   - Открыть `/expenses` и `/expenses/approvals` с реальной тестовой сессией.
   - Зафиксировать активный `casino_id`, параметры запросов, ответы backend и значения фильтров.
   - Сопоставить полученный `casino_id` со строками этого филиала.

2. **Исправить подтверждённую причину пустого `/expenses`**
   - Если запрос запускается до установки филиала или остаётся на старом `casino_id`, синхронизировать его с `CasinoProvider.activeCasinoId` и не показывать пустое состояние до завершения определения филиала.
   - Если backend возвращает строки, но UI их отбрасывает, нормализовать устаревшие session-фильтры Super Admin: Source = All, Status = All; дату не менять молча, но показывать понятный активный диапазон и рабочий Reset.
   - Не ослаблять RLS и не включать межфилиальный список: на домене филиала показывать только его данные.

3. **Исправить роль Super Admin в интерфейсе**
   - Включить Super Admin в управленческий режим `/expenses`.
   - Вернуть ему Source, backdate, Approve, Edit и Delete на строках.
   - На `/expenses/approvals` сохранить очередь только pending-расходов; если pending нет, показывать корректное `No pending expenses`, а не считать это поломкой общего списка.

4. **Добавить hard delete только для Super Admin**
   - Отдельная кнопка `Delete` с подтверждением на обоих экранах.
   - Перед реализацией проверить связи конкретного расхода с `fin_wallet_tx` и аудитом.
   - Удалять строку и связанные финансовые последствия одной серверной операцией, чтобы Wallets/Expected не расходились. Нельзя сначала удалить UI-строку, оставив проведённое движение кошелька.
   - Для остальных ролей оставить существующие Approve/Cancel/Void правила без изменений.

5. **Проверка**
   - Под Super Admin на домене каждого затронутого филиала: список `/expenses` виден и ограничен доменом; Approvals показывает фактические pending строки; hard delete удаляет выбранную строку и её финансовый эффект без остатка.
   - Проверить, что manager/cashier видят свои данные как раньше и не получают hard delete.
   - Typecheck, целевые тесты, build; затем bump версии. Без deploy/publish.
