# Единая модель доступа: сетевые учётки vs учётка одного казино

## Новая логика (простая)

1. **Сетевая учётка** — работает на любом поддомене одинаково. Никакого «домашнего» казино: всё, что она видит в меню, работает и с данными того казино, на чьём поддомене человек находится.
2. **Локальная учётка** — привязана к списку своих казино. На чужом поддомене доступ закрывается сразу (сообщение о запрете), а не пускает внутрь с пустыми экранами.

Поле «домашнее казино» остаётся только как значение по умолчанию для входа без поддомена и правами больше не управляет.

## Что показала проверка базы

- **86 таблиц и около 190 правил доступа** сравнивают казино с «домашним» из профиля (`get_user_casino_id`). Это и есть причина «частичных» экранов.
- Расходы: суперадмин читает, но подтвердить/изменить/удалить может только в домашнем казино.
- Слоты (`cage_slots_*`) — проверка `cs_can_view` жёстко зашита на домашнее казино, поэтому дроп (открытый кэш) виден, а результат смены слотов — нет.
- Игроки: карточка игрока видна всем (правило «все авторизованные»), а история — транзакции, сессии, средние ставки, позиции, заметки, promo, чеки — режется по домашнему казино. Отсюда «имя есть, истории нет».
- Функция `user_has_casino_access` знает только super_admin и finance_manager — boss и general_manager в неё не попадают.
- В интерфейсе general_manager не входит в список сетевых ролей.

## Сетевые учётки

Полный доступ ко всем казино: **admin (Super Admin), gm (General Manager), igor (Boss), michael (Manager + Finance)**.
Сетевыми остаются и те, у кого уже проставлен доступ ко всем казино: surveillance (alex, andrew, cctv, vladimir), account manager (amanager).
`michaelm` — локальная на Mwanza + Mbeya. Остальные — только своё казино.

## Что делаю

### 1. Одна функция доступа
`public.has_casino_scope(_uid, _casino_id)` — доступ есть, если казино есть в списке доступа пользователя, либо это казино из его профиля, либо роль сетевая. `user_has_casino_access` переводится на ту же логику. Для сетевых учёток заполняю список доступа явно по всем казино.

### 2. Массовая замена правил доступа
Прохожу **все 86 таблиц** и заменяю сравнение с домашним казино на проверку доступа, сохраняя ролевую часть условия без изменений. Основные блоки:

- Касса и деньги: `expenses`, `transactions`, `shifts`, `cash_counts`, `cash_count_snapshots`, `cage_transfers`, `cashless_transactions`, `bank_checks`, `transaction_cancellations`, `business_day_closures`.
- Слоты: `cage_slots_*` и функции `cs_can_view` / `cs_can_write` / `cs_can_approve`.
- Столы и фишки: `gaming_tables`, `table_daily_results`, `table_tracker`, `table_head_count`, `chip_*`.
- Игроки: `players` (создание), `player_cards`, `player_notes`, `player_crm`, `player_groups`, `group_members`, `player_daily_avg_bets`, `player_position_history`, `client_sessions`, `casino_visits`, `kyc_reviews`, промо и лотереи, магазин.
- Питы и персонал: `pit_rota`, `breaklist`, `dealer_attendance`, `employees`, `staff_rota`, `staff_attendance`, `staff_warnings`, `attendance_*`, `payroll_*`.
- Финансы: `fin_*` (кошельки, движения, бюджет, закрытия дня и месяца, курсы, прочие доходы).
- Прочее: `incidents`, `cctv_observations`, `activity_logs`, `casinos`, `profiles`, `user_roles`, `user_casino_access`, `system_locks`, POS-закупки.

### 3. Интерфейс
- `general_manager` добавляется в сетевые роли в `src/lib/casino-context.tsx`.
- Если у учётки нет доступа к казино этого поддомена — понятный экран запрета с выходом, вместо пустых страниц.
- Переключатель казино показывается только тем, у кого доступов больше одного.

## Чтобы ничего не сломать

- Расширяется только «какое казино», роли и права на действия не трогаются: кассир останется кассиром, локальная учётка не получит ни одного лишнего казино.
- Правила пересоздаются по одной таблице, единой миграцией, с сохранением исходных названий и ролевых условий — откат возможен одной обратной миграцией.
- Проверка `has_casino_scope` работает через служебную функцию, поэтому рекурсии в правилах не будет.
- Отдельно проверяю таблицы, где сегодня доступ открыт всем авторизованным (`players`, кэш дропа) — их не расширяю, а при необходимости сужаю до того же правила доступа.

## Проверка после изменений

1. Прогон от имени каждой учётки (admin, gm, igor, michael, michaelm, локальный livemb) по каждому казино: считаю количество видимых строк в расходах, сменах, транзакциях, результатах столов, сменах слотов, роте, персонале, финансах — у сетевых должно совпадать с фактическим количеством, у локальных быть нулём в чужом казино.
2. Живая проверка на Mbeya: Expenses (создать/подтвердить/удалить), результат слотов, карточка игрока с полной историей, Table Check.
3. Запуск security-линтера и прогон тестов доступа (`src/test/access-matrix.test.ts`).

## Технические детали
- Миграция: `has_casino_scope` (`STABLE SECURITY DEFINER`, `search_path = public`) + DROP/CREATE политик по перечисленным таблицам + обновление `cs_can_*` и `user_has_casino_access` + заполнение `user_casino_access` для сетевых учёток.
- Гранты Data API не меняются.
